# Taste Learnings
- Communicates in Spanish (informal, uses "bueno", "te comento"). Confidence: 0.9
- References code locations using absolute Windows-style paths (e.g., `C:/YaRidersAPP/...` or `@path\To\File.ext`). Confidence: 0.8
- When reporting a bug, provides detailed step-by-step reproduction of the observed behavior (action → observed → expected). Confidence: 0.85
- Asks for analysis/diagnosis of bugs before requesting a fix ("me ayudas a analizar que seria ese bug"). Wants to understand root cause first. Confidence: 0.8
- Prefers adding informative subtitles/labels below menu items when a feature has a prerequisite or access requirement (e.g., "you must have prior access to..."). Confidence: 0.85
- When clarifying UI behavior, prefers explicit, user-facing text rather than relying on tooltips or hidden info. Confidence: 0.7
- When reporting a flow that "doesn't work", walks through the exact sequence of actions taken (login → tap menu → select option → logout → re-login) to reproduce it step-by-step. Confidence: 0.9
- Insists on persistence across session boundaries (logout/login cycle) for user preferences and selections — expects local storage to survive the session even when other session data is cleared. Confidence: 0.85
- Uses casual Spanish confirmations like "si dale" to greenlight implementation without further discussion once a fix is proposed. Confidence: 0.75
- Very attentive to whitespace/spacing in UI components (bottom sheets, headers, handles, stacked cards) — flags subtle padding/margin issues that make layouts look "feo", leave blank gaps, or leave sections visually "pegado" (glued) together, and wants proper separation between distinct stacked blocks. Confidence: 0.85
- Prefers compact collapsed/minimized UI states (e.g., bottom sheets) — asks to reduce fixed heights so more of the underlying content (map) stays visible. Confidence: 0.75
- Gives iterative, incremental UI feedback ("esta mejor pero..."), acknowledging progress then requesting one small adjustment at a time. Confidence: 0.8
- When an attempted fix doesn't resolve the issue ("sigue igual"), points the assistant to a parallel/analogous component elsewhere in the codebase that already works correctly and asks it to investigate the difference ("revisa como se comporta la parte de X que tiene este mismo sheet y alli no tiene espacios"). Prefers using existing working implementations as reference rather than re-deriving from scratch. Confidence: 0.85
- Prefers "fetch once per component mount" semantics for data loading on screens: wants fetches to run only on initial mount, and only re-run on explicit user action (pull-to-refresh, reload). Uses `useRef` flags instead of `useState` flags to avoid the effect re-firing when the flag itself changes. Explicitly states "solo se ejecute una vez y si la persona recarga ahi si se vuelve a consultar". Confidence: 0.9
- Prefers grouping contextual action buttons directly next to the entity they relate to (e.g., chat with driver placed beside the driver info / call button) rather than in a separate, generic "actions" block below. Wants compact icon-style buttons (40x40 circular) when actions sit alongside entity info. Confidence: 0.85
- When formalizing flow states, expects a companion .md doc in repo docs/ with terminology table plus exact API consumption (endpoints, params/bodies for state changes), focused on driver side. Confidence: 0.85
- Prefers driver action buttons to perform real backend state transitions rather than notify-only side effects (e.g., replace manual "notificar" button with a state change that also triggers the push). Confidence: 0.8
- Prefers separate state vocabularies per business flow (e.g., individual carrera vs pedido/delivery) even when they share the same API resource, because backend push notifications must differ by flow. Confidence: 0.8
- Insists on preserving established domain/user-facing terminology (e.g., \"arrendamiento\" not \"carrera\") — explicitly forbids removing/renaming existing terms and prefers leaving wording as-is when in doubt. Confidence: 0.9
- Prefers analysis-first scoping for new features: asks for panorama of current state + implementation plan (what already exists, what needs building, how to display it) before authorizing implementation. Confidence: 0.8
- Prefers reusing existing backend endpoints over adding new APIs: asks explicitly whether a new API is needed and expects assistant to cross-check both frontend and backend repos (code + endpoint docs) when scoping. Confidence: 0.8
- Prefers collection GET endpoints to return 200 with empty array instead of 404 when there are no results (e.g., empty chat should return vacio). Confidence: 0.8
- Prefers chat UIs as overlay modal covering ~70% of current screen (bottom-sheet style) rather than a separate navigation screen/view. Confidence: 0.85
- When applying state-based visibility, prefers to keep informational context (e.g., client name/photo block) always visible and hide only the action button (e.g., chat) rather than hiding the whole section. Confidence: 0.8
- Prefers chat images to be tappable to open a shared fullscreen zoomable viewer (pinch, double-tap, +/- controls), reusing the existing FullscreenImageViewer implementation from ChatReserva.js consistently across all chat variants rather than per-screen variants. Confidence: 0.85
- When proposing files to change, provides a candidate list with absolute paths but asks assistant to validate actual usage (which chats/screens are really in use via navigation/usage search) before implementing. Confidence: 0.75
- Prefers to remove purely decorative UI elements that have no current or planned functionality (e.g., decorative barcode in ticket UI is irrelevant if it will never have functionality). Confidence: 0.75
- Prefers to avoid duplicating information already visible elsewhere on the same screen (e.g., omit item list from summary when items are listed above, show only final totals). Confidence: 0.75
- Prefers UI colors to reuse the existing palette/backgrounds rather than introducing one-off contrasting colors that appear nowhere else and don't complement the design. Confidence: 0.85
- Prefers consistent card treatment across related sections on the same screen — product/item cards should share the same relief, border, shadow and elevation as the summary card rather than having distinct styles. Confidence: 0.75
- Prefers to hide the contracting client/customer phone number everywhere (lists, detail sheets, mappings) for privacy, while keeping rider/commerce phone numbers visible and callable. Confidence: 0.9
- When a screen offers chats with multiple counterparties (e.g., commerce vs driver), wants entry points placed next to each person for clarity, but keeps chat modal headers in the same established style (e.g., orange) rather than distinct per-variant color schemes. Confidence: 0.85
- Prefers chat quick-replies to be role-aware: commerce/seller presets should be order-status updates (confirmed/preparing/ready) while customer presets stay as questions/thanks, rather than sharing one generic set. Confidence: 0.75
- Prefers quick-reply/action chips to wrap to multiple lines rather than horizontal scroll that hides actions off-screen to the right. Confidence: 0.8
- Prefers user-facing localized status labels over raw backend enum strings in Pedidos/trip UIs — never shows uppercase codes with underscores like EN_COMERCIO, maps them per flow (pedido vs carrera normal). Confidence: 0.85
- Prefers read-only backend validation when auditing behavior (e.g., push notifications in chat / state-change APIs) — explicitly asks to validate without making changes. Confidence: 0.8
- Expects chat modal headers to show the counterpart's identity (name, photo/avatar, order context) rather than own business info, and flags missing counterpart photo as a bug. Confidence: 0.85
- Prefers close (X) icon in white on colored chat/modal headers (orange/dark) for contrast, flags gray X as looking bad. Confidence: 0.85
- Prefers push-notification-triggered auto-refresh/refetch on detail and list screens, same as chats do on push, over requiring manual reload — expects order/trip details and commerce orders/reservas to refetch when a push arrives. Confidence: 0.85
- Prefers reusing the same summary view and same up-to-date API across screens when showing the same metrics, so counts stay identical everywhere rather than maintaining separate layouts/data sources per screen. Confidence: 0.85
- Wants the exact API behind each UI action (method, endpoint, payload shape) spelled out for manual/Postman testing and to disambiguate similar features like multiple chats. Confidence: 0.85
- When a fix fails repeatedly, especially for systemic bugs affecting multiple variants, prefers adding temporary action/event logs to provide a diagnostic panorama of where it fails rather than blind re-fixes. Confidence: 0.8
- Proactively tests a suspected bug across parallel implementations/variants (e.g., all chat screens) to establish systemic scope rather than treating it as isolated to one screen. Confidence: 0.75
- Prefers images (e.g., payment evidence/comprobante) to render inline in-app with zoom support rather than requiring opening an external browser URL. Confidence: 0.85
- Prefers pragmatic quick fallbacks reusing already-installed libraries (e.g., WebView for images that won't render) to avoid prolonging a task rather than extended root-cause debugging. Confidence: 0.7
- Prefers orders/reservations tabs to show both actives and full history (completed/cancelled) sectioned together rather than actives-only filtering, keeping the same sectioned pattern across user/commerce/driver roles with role-appropriate adaptations (e.g., no profile filter for end user). Confidence: 0.8
